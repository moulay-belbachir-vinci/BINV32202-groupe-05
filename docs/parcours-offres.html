Documentation d'architecture

Afficher les offres, de React à SQLite

Cette page décrit le parcours actuellement implémenté dans Gesta et recense les fichiers à prévoir pour ajouter un filtre par période. Elle ne modifie pas le comportement de l'application.

1. Architecture générale

frontend (React + Vite)
  main.tsx → App.tsx → pages → hooks → services HTTP → API /api
                         ↓
                    components

backend (Express + TypeScript)
  main.ts → initializeDatabase → app.ts
                                  ↓
       middlewares → controllers → services → repositories → SQLite
                                  ↓
                         mappers / models

SQLite
  migrations/001_initial.sql → offers
                             → companies
                             → academic_years → periods

Le frontend suit un découpage de type MVVM : les pages assemblent l'interface, les hooks portent l'état et le cycle de vie, les services effectuent les appels HTTP et les composants affichent les données. Le backend sépare la route HTTP, les règles métier et la persistance. Les mappers empêchent d'exposer directement les lignes SQL : une ligne OfferDbo devient un objet métier puis un OfferDto.

En développement, le navigateur appelle /api/offers. Le proxy Vite de frontend/vite.config.ts retire /api et transmet la requête à l'API backend sur le port 3000.

2. Parcours d'affichage des offres

1

Montage de l'application et contrôle de session

frontend/src/main.tsx monte <App /> dans #root avec BrowserRouter. Dans frontend/src/App.tsx, useAuth vérifie la session. Si l'utilisateur connecté peut lister les offres, la route /offres rend OffersPage et lui transmet le jeton ainsi que la fonction de déconnexion.

2

Chargement côté page

frontend/src/pages/OffersPage.tsx appelle useOffers(token, onUnauthorized). Le hook frontend/src/hooks/useOffers.ts initialise l'état offers, isLoading et error, crée un AbortController et annule la requête lors du démontage.

3

Appel HTTP et validation de la réponse

frontend/src/services/offers.service.ts envoie GET /api/offers avec l'en-tête Authorization. frontend/src/utils/api.ts vérifie le statut HTTP puis frontend/src/utils/guards.ts valide la forme du JSON comme une liste d'Offer. Une réponse 401 est transformée en déconnexion par le hook ; les autres erreurs sont affichées.

4

Proxy Vite puis middleware Express

Le proxy transforme /api/offers en /offers. Dans backend/src/app.ts, la route est protégée par backend/src/middlewares/authenticate.ts : le jeton est vérifié et l'utilisateur est relu en base. Puis authorize(canListOffers) refuse l'accès à un contact qui n'a pas le droit de consulter les offres.

5

Contrôleur et visibilité métier

backend/src/controllers/offers.controller.ts reçoit GET /offers, appelle offersService.listOffers(getCurrentUser(req)) puis mappe chaque résultat avec toOfferDto. Dans backend/src/services/offers.service.ts : l'administrateur voit tout, l'étudiant voit les offres PUBLISHED, et un contact déposant voit ses propres offres.

6

Requête SQL et jointures

backend/src/repositories/offers.repository.ts convertit le filtre métier en paramètres SQL et interroge offers. La requête joint companies, academic_years et periods pour produire le nom court de l'entreprise, le libellé de l'année et le code de période. Le tri est décroissant par année académique puis par date de création. Le schéma et les relations sont définis dans backend/src/db/migrations/001_initial.sql.

7

Retour vers le tableau React

Le mapper backend/src/mappers/offer.mapper.ts expose le DTO public. Le hook met à jour son état, puis OffersPage.tsx affiche l'état vide, l'erreur, le chargement ou frontend/src/components/OfferTable.tsx. Le tableau affiche le titre, l'entreprise, l'année, la période (PERIOD_LABELS) et le statut.

3. Fichiers concernés par un filtre par période

Le modèle possède déjà un champ period avec les codes P1, P2 et OTHER. Le filtre propose aussi explicitement « Toutes les périodes » : cette valeur d'interface est convertie en absence de paramètre, par exemple /offers. Les autres choix circulent jusqu'au repository sous la forme ?period=P1.

frontend/src/components/OfferTable.tsx Pas forcément à modifier : le tableau consomme déjà une liste filtrée. À modifier seulement si le contrôle est intégré au tableau. Optionnel

backend/src/controllers/offers.controller.ts Lire et valider le paramètre (valeur unique, code autorisé), puis le passer au service. À modifier

Pas de migration nécessaire pour P1/P2/OTHER : periods.code existe déjà et la jointure est déjà présente. Une migration ne serait utile que pour ajouter un nouvel attribut persistant, un index dédié ou une nouvelle notion métier.

4. Cas d'un filtre par intervalle de dates

Si « période » signifie une plage calendaire plutôt qu'un code P1/P2/OTHER, le frontend devrait envoyer deux paramètres validés, par exemple startDate et endDate. Le repository pourrait filtrer periods.start_date et periods.end_date, car ces colonnes existent déjà dans la base. Il faudrait alors aussi décider si le filtre sélectionne les périodes entièrement incluses ou celles qui se chevauchent.

Dans ce second scénario, les mêmes fichiers sont concernés, avec en plus frontend/src/models/offer.ts ou un nouveau type de paramètres si l'interface doit représenter les dates, et des tests de bornes (date invalide, début après fin, chevauchement).

Document produit à partir de l'état du dépôt observé le 30 octobre 2026. Les chemins sont relatifs à la racine du projet.
